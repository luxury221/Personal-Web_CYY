CASE 01 / RETRIEVE

MultiRank-RAG

复杂 PDF 多模态 RAG · GraphRAG · 证据链问答系统

2026

TYPE — PERSONAL RESEARCH & ENGINEERINGCORE — MULTIMODAL RAG · GRAPHRAG · RERANKSTATUS — PUBLIC / REPRODUCIBLE

PRIMARY RESEARCH FLAGSHIP
RESEARCH PROBLEM

复杂 PDF 问答的失败往往不是模型不会回答，而是正确证据从未被可靠召回。答案可能跨越正文、表格、图片、图注和多页关系；传统 chunk-based RAG 一旦把文档压成匿名文本块，就会丢失结构、引用和跨模态联系。

KEY INSIGHT

Retrieval 应该作用于结构化证据，而不是孤立 chunk。

把 text / table / figure / caption / equation 统一为 evidence nodes，并保留 page、bbox、reading order 与引用关系，让后续召回和重排能够利用文档结构。

METHOD

从候选召回到 evidence-chain verification。

Query Planner 根据题型改变 retrieval route；MultiRank G0–G4 逐层引入语义、图传播、bridge evidence、reference matching 与 visual grounding，再由 verifier 检查证据链。

ENGINEERING / RESEARCH DECISIONS

01 / WHY NODES

为什么不是普通 chunk？

复杂 PDF 的答案依赖版面和引用关系；匿名 chunk 会让表格、图注、公式和跨页上下文失去结构身份。

02 / WHY GRAPH

为什么加入 GraphRAG？

语义相似度不等于证据关系。结构、reference、entity 与 semantic edges 用于找 bridge evidence 和跨节点链路。

03 / WHY ABLATION

为什么保留 V0–V5？

为了回答“哪个模块真的有效”。简单文本任务作为负对照，避免系统只在复杂任务上看起来更强，却在基础能力上发生回退。

CURRENT LIMITATION

瓶颈已经前移到候选召回。

MMLongBench-Doc 上视觉模态覆盖能够被后续模块恢复，但 absolute visual recall 仍然偏低，说明第一阶段 BM25 candidate generation 是当前主要限制。

NEXT

优先改 candidate generation，而不是继续堆 reranker。

下一步关注 visual-first retrieval routing、adaptive multimodal candidate generation 与 learned evidence graph，让正确视觉证据更早进入候选集。

CASE 02 / REASON

孔明职配 · Agentic Career System

岗位知识 RAG · 多智能体协作 · 证据化匹配与面试

2026

TYPE — TEAM PROJECTROLE — AGENT · RAG · FULL STACKPRINCIPLE — EVIDENCE BEFORE SCORE

AGENTIC SYSTEM FLAGSHIP
DESIGN PROBLEM

求职并不是一个 Prompt 能完整覆盖的单步任务。简历解析、岗位检索、匹配判断、简历策略与面试评估拥有不同输入、输出和验证标准；如果全部塞给一个 Agent，自由文本状态会快速变得难以追踪。

KEY INSIGHT

Multi-Agent 的价值来自边界，而不是 Agent 数量。

六类角色共享 AgentContext / AgentEvent / AgentArtifact，明确每一步的输入、证据、输出和下一动作，避免 Agent 之间通过自由聊天传递隐式状态。

EVIDENCE MODEL

评分先绑定证据，再交给模型解释。

岗位库保留来源、抓取时间与内容哈希；匹配维度绑定 JD 与简历依据；面试追问根据上一轮证据选择澄清、深挖或换维度。

ENGINEERING DECISIONS

01 / WHY MULTI-AGENT

不同阶段有不同验证标准。

检索需要来源，匹配需要维度化证据，面试需要连续状态；拆分角色可以让错误更容易定位。

02 / WHY STRUCTURED STATE

聊天历史不是长期记忆。

偏好、证据、任务与反馈作为结构化状态维护，并区分预测分与新证据验证后的实证分。

03 / WHY VERIFY

工作流必须能回归测试。

十余个 verify 脚本覆盖评分、成长闭环和完整用户流程，避免 Agent Prompt 修改后只靠人工点击判断是否退化。

CURRENT LIMITATION

Agent 越多，错误传播和状态漂移越值得警惕。

角色拆分能提高可控性，但也引入跨 Agent 的信息压缩、状态更新和责任边界问题。

NEXT

把“哪些状态能让模型总结”变成显式设计问题。

后续更关注 memory update policy、error attribution 与 deterministic state machine，减少多 Agent 系统的隐式耦合。

KEY INSIGHT

AI 建议和最终责任必须分离。

AI 只输出建议评分与依据，教师保留最终确认权；作业发布时固定题目、答案与 rubric 快照，减少不同批次或模型变化造成的评分漂移。

SYSTEM INSIGHT

AI 功能要成为平台能力，而不是同步 API 调用。

Redis 队列、8 路 Worker、MinIO、API/Auth/Worker 分离、Theia 与 Judge0 让批改、存储和代码执行可以异步、隔离并独立扩展。

ENGINEERING DECISIONS

01 / WHY HITL

教师保留最终控制。

教育评分涉及责任和一致性，模型更适合作为有依据的建议层，而不是不可申诉的最终裁决者。

02 / WHY ASYNC

批量 AI 任务不应阻塞 Web 请求。

队列和 Worker 把长耗时模型任务与交互请求解耦，也为限流、重试和水平扩展保留空间。

03 / WHY ISOLATION

代码执行必须与业务服务隔离。

Theia + Judge0 将用户代码放进独立执行链路，避免把不可信代码直接交给主业务容器。

KEY INSIGHT

多模态交互的核心是状态协调。

Qwen 实时语音、ASR、WebSocket、MediaPipe 与 3D 动作同时工作时，系统必须知道谁可以打断谁、什么时候结束、哪个事件应当改变角色状态。

PRODUCT FLOW

把复杂 3D 流程收敛成普通用户可走通的链路。

文本/图片/预设进入 Meshy 生成，再通过 8 点标注、任务轮询与动作预览完成辅助绑骨，最后进入场景和实时会话。

INTERACTION DECISIONS

01 / WHY WEBSOCKET

实时语音需要持续双向状态。

WebSocket 支持持续音频流、打断和会话生命周期，比一次性 HTTP 请求更适合实时语音。

02 / WHY EVENT STATE

手势不是装饰事件。

手势、语音和 3D 动作都可能改变当前会话，必须通过状态与优先级协调，而不是各自独立触发。

03 / WHY DATA LOOP

实时交互也应该可复盘。

会话历史、事件、摘要和录屏被保存，使实时体验不只存在于屏幕上，而能成为后续分析的数据。

CURRENT LIMITATION

语音、手势、动画与模型生成并发发生时，状态冲突与延迟会被用户直接感知。多模态能力越多，交互一致性越难维护。

NEXT

进一步把 event priority、interrupt policy 与 session state machine 显式化，并对端到端延迟和冲突恢复做系统级评测。
